在固定的 12 条 fmt 查询上，原生搜索返回 6,419 bytes，目标锚点正文覆盖 12/12；文件摘要加固定下钻返回 95,835 bytes，正文覆盖 11/12。两者的目标文件候选覆盖均为 12/12。模型调用为 0。

[缓存检索快照报告](current/README.md)使用相同输入复测有界缓存及紧凑证据版本，原生搜索为 6,419 bytes，摘要加固定下钻为 97,402 bytes，正文覆盖仍为 12/12 与 11/12。两份快照分别保存源码、协议和逐查询响应。

## 固定输入与测量

输入复用 [公开协议](../code-index-20261106/protocol.json) 中的三份 fmt 头文件、12 条预登记查询及定义锚点，fmt commit 为 `0fc31633e7d53ac895ae0a688b83b7d44f0b0c1f`。脚本校验协议、tar 和逐文件 SHA-256，查询范围统一为三份头文件。该样本是定向静态查询集。

A 直接调用归档实现中的 `Toolbox.search_code`。B 调用 `Localization(toolbox, mode="bounded").search`，每个候选文件读取首个命中前 20 行开始的 200 行窗口；下钻只依赖候选响应。评分随后核对预登记锚点及实际返回源码正文。C 使用相同输入执行无证据回退检查。

每条查询保留五次重复，共 60 份逐查询原始记录。A/B/C 按查询与重复轮换执行顺序，B 下钻随后执行。测量源码封存在 `production-source.tar`，运行时从隔离快照导入；[protocol.json](protocol.json) 提供全部代码和输入哈希，`source_git_head` 描述快照来源提交，精确运行内容由逐文件哈希标识。以下数据对应这份冻结快照；当前检索实现的缓存、分页和输出预算由源码回归及独立 A/B/C 实验核验。

## 固定候选格式

12 条查询产生合计 59 条匹配记录；每条保留相同 candidate ID、路径、行号、300 字符上限正文及顺序。扁平格式逐行重复路径，分组格式按文件组织同一批记录。此表是独立的纯格式对照，序列化包含统一的 candidate ID。

| 格式 | 总 bytes | 正文 JSON 载荷 | 路径 JSON 载荷 | 格式化墙钟中位数 μs | 格式化 CPU 中位数 μs |
| --- | ---: | ---: | ---: | ---: | ---: |
| 扁平记录 | 11,041 | 3,051 | 1,073 | 7.394 | 6.483 |
| 按文件分组 | 10,074 | 3,051 | 312 | 10.471 | 9.608 |

该固定输入上，分组格式减少 967 bytes（8.76%），格式化耗时增加。共同匹配流生成的查询墙钟/CPU 中位数为 0.495/0.494 ms，单独记录于原始结果。这里的体积和耗时对应格式转换；Agent 定位效率、模型 token 和修复成功率均为未测量指标。
