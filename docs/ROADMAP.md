# 下一阶段开发计划

按可验证结果推进，不预先扩展为通用 Agent 平台。当前入口仍是本地 CLI。

| 顺序 | 工作 | 验收标准 |
| --- | --- | --- |
| 0 | 在标准 Linux Docker 主机完成当前隔离验收 | 3 个 Docker 集成测试实际通过，保存 image ID 和日志 |
| 1 | 单任务最小事件状态机 | 事件版本、运行/命令状态、SQLite 事务写入，JSONL 可重新导出 |
| 2 | Checkpoint 与故障恢复 | 在模型/工具/验证边界注入崩溃；重启后不重复计费、不重复应用修改 |
| 3 | 轨迹重放与确定性比较 | 区分只读回放、工具回放和模型重跑；校验 commit、快照及工具版本 |
| 4 | 真实 C++ 任务集 | 选择许可允许的 5–10 个小型真实历史 bug，固定提交和可信回归，不编造修复率 |
| 5 | C++20 Linux 执行器 | 单独实现进程树、pidfd/超时、资源限制、受限 IPC；与 Python 执行器对照故障测试 |
| 6 | 小规模真实模型评测 | 用户先确认费用；记录每任务基线、成功/失败、tokens、耗时和实际费用 |

Checkpoint 首先以 SQLite 为事实来源，避免现在两份日志的崩溃尾部差异成为恢复歧义。
付费调用应具有可审查的“请求已发出但响应未知”状态，不承诺网络重试可以 exactly-once。
工具应区分幂等读取、源码编辑和编译执行，再定义恢复策略。

真实任务集优先考虑独立库中的边界检查、整数范围、对象生命周期和解析器问题；
固定测试不交给 Agent 修改，补充隐藏测试与必要的 ASan/UBSan。
评测报告分别列 Harness 正常运行率、补丁应用率、复现通过率及隐藏测试通过率，
只报告实际观测值。当前一个手写缺陷与 Mock 脚本不能用来估计模型能力。

暂不纳入：多 Agent 调度、分布式执行、大型前端、任意 shell 权限、自动提交远程 PR。
